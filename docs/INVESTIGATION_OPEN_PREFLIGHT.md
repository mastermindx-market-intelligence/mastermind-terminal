# Unified Investigation OPEN: source preparation

This candidate does **not implement OPEN**. The baseline read and Saved mutation
handlers keep their existing common guard. The normal installer remains CLOSED.
No configuration, SQL, service, admission record or user operation is changed.

`ops/investigation-open-preflight.sh --target beta --target-sha <40-hex>` is a
read-only **future native invocation**, not an instruction to run it while
runtime effects are held. It sources the existing `terminal-build.sh` library
through its incumbent sourced-file entrance and uses its fixed beta profile.
It requires source containment, the real ordinary accepted-runtime validator
(including provenance, pending-attempt refusal, rollback baseline and live
marker/build binding), an exact requested/installed SHA match, and the existing
CLOSED selected-unit/serving-process verifier. It creates no parallel accepted
record. Production and arbitrary profiles are unsupported.

A qualified installation returns `SOURCE_PREPARATION` and exit 78, with four
precise missing source contracts. It never returns ready or activates OPEN.
`ready=true`, supplied attestation JSON, health, flag state or an empty pending
count cannot replace these contracts.

## Remaining source contracts and held observations

1. **All-ingress/direct-RPC/drain observer.** It must consume the incumbent
   qualified fleet/ingress identity and actual database-role closure evidence,
   with an exhaustive current set and bounded observation identity. One unit's
   CLOSED setting cannot establish other API instances or direct RPC closure;
   closing admission does not cancel already-admitted requests. The retained
   S11 record retains a fleet-metadata effect whose original receipt/generation
   is unavailable. The source at Mastermind 968e1a62 classifies the named
   OWNER_RESULT_INVALID as returned-owner JSON/schema/readiness validation,
   wrapped as REFUSED; it is not inherently a permission preflight. This does
   not clear or retry the historical effect. The Fleet contract supplies
   gateway/tunnel health, not ingress closure, in-flight drain or an admission
   epoch. Its repair/enrollment cannot substitute for this different contract.
2. **Original-operation inventory and live receipt binding.** The source-only
   `ops/investigation_operation_observer.py` now reads one explicit original
   principal/key through the incumbent `read_investigation_operation_v2` RPC
   callback, with subject checks before and after. It accepts no receipt JSON
   entrance and never calls reconcile/apply/retry. Missing/changed IDs, a read
   miss, partial lineage, a capacity label or a possible later completion stay
   unresolved. A commit needs the original expected revision/materialized
   manifest digest; these must not be copied from the returned record.

   Under exact qualified 0030, a stored `not_applied` receipt is a terminal
   no-effect fence: reconcile and apply hold the same per-operation lock;
   reconcile stores the result, and any later same-key apply returns that
   prior result or an idempotency conflict before writing. The unstored
   capacity answer cannot be proved by a SELECT miss and is not accepted.
   The observer reports only recorded facts: it does not certify current SQL,
   grant state, receipt immutability, inventory completeness or cutover.

   Actual complete inventory and authorized live binding must consume original
   operation identities and definitive same-operation receipts/fences. The
   retained CREATE/15 UNKNOWN labels do not provide an authoritative complete
   machine-readable operation inventory. An empty caller-provided list, receipt
   miss, elapsed time or another operation cannot establish reconciliation.
3. **Lawfully admitted schema/grants receipt verifier.** It must bind the exact
   approved migration bytes, database/schema target, application/readback and
   actual grants to the installed API contracts. SQL0030's original T03k refusal
   and unaccepted return remain held. No new receipt issuer is invented here.
   Dependent migrations are required by their actual enabled scope; 0048 is not
   a blanket Investigation prerequisite.
4. **Unified OPEN adoption/recovery transaction.** Only after those real
   qualifications exist can a source-owned transaction change the selected
   configuration and prove process adoption, preserving source/runtime/rollback
   identities and original uncertain outcomes. It must extend the existing
   owner's custody rather than create a second lifecycle or accepted registry.
   A configuration or restart lost response must not trigger blind repetition.

These missing contracts are engineering inputs; no historical-owner ACK is
required. Their positive runtime truth cannot be manufactured from fixtures.
This preparation exposes the exact gaps without claiming the S17 outcome done.

## Prospective native capture participant

Before its first private retention PUT, the native server uses its incumbent

After the synchronous incumbent producer returns from all original writes and
exact readbacks, `complete_investigation_native_capture_v1` records retained for

The native browser-facing route accepts no completion or server-role input.

Canonical save and native retention remain separate dispositions. The same
operation lock serializes canonical apply/reconcile against the reservation.

its result is not an ingress/drain or cutover attestation. The current UI keeps

establish closure; neither local journal bytes nor canonical not-applied alone

Partial writes, lost completion acknowledgements, mismatched generations and
unavailable rights remain UNKNOWN. No TTL, empty handler count, object existence,

Investigation guard remains shared, and the normal installer remains CLOSED.
Actual isolated socket-only PostgreSQL controls prove only their disposable

## Atomic source composition on the incumbent SQL path

`ops/investigation_closed_composition.py` is an import-only source assembler,
not an SQL executor or qualification receipt issuer. It accepts only the exact
0030 bytes with SHA256
`e98d5a59cfb1932ebf4e562ecf89b6d08b7a5c9365b3e2fbe0b612eaaeff4694`.
The `.txt` fixture preserves those bytes; it is not a migration namespace entry.

One outer DO dynamically executes the unchanged pinned source, then revokes
EXECUTE on the two declared seven-argument v2 mutation functions from PUBLIC,
anon and authenticated, and asserts the two named roles have no effective
EXECUTE privilege. This addresses their regrant window without editing 0030,
adding a global lock or requiring connection reuse. It does not claim closure
of unknown RPCs/admin roles or already-admitted calls.

PostgreSQL supports utility commands through PL/pgSQL EXECUTE; its executor
accepts utility results and passes atomic context to a nested DO. The pinned
source contains no transaction control. Without a new exception handler or
commit, an unhandled failure aborts the statement's transactional changes.
This is a source inference from the
[PL/pgSQL command documentation](https://www.postgresql.org/docs/15/plpgsql-statements.html),
[transaction documentation](https://www.postgresql.org/docs/15/tutorial-transactions.html),
and upstream [dynamic executor](https://github.com/postgres/postgres/blob/REL_15_STABLE/src/pl/plpgsql/src/pl_exec.c)
and [utility dispatcher](https://github.com/postgres/postgres/blob/REL_15_STABLE/src/backend/tcop/utility.c),
not an executed database experiment or a claim about an observed server version.

The actual incumbent `supabase_apply` splitter sees one mutating statement and
retains the exact embedded bytes after its comment preparation. Original schema
readback queries plus the additional grant readback are front-loaded so the
helper's first-anchor metadata parser does not select inner comments. Tests
reject changed source, split BEGIN/COMMIT, removed final revokes/assertions and
added error swallowing. A fake QueryRunner verifies the owner's failure result
and single mutation submission; it cannot prove engine rollback.

The composed source has a new identity and still needs its own lawful source
and runtime qualification on the incumbent carrier. It does not clear T03k,
execute/replay the held qualifier, apply SQL, prove fleet/drain/original-operation
outcomes, or authorize OPEN. Actual server/helper acceptance and rollback remain
unexecuted. No alternate SQL transport or credentials are introduced.

## Existing TypeScript read and draft consumer

The Python observer does not substitute for the application's operation reader.
The TypeScript service, authenticated GET and both existing save consumers now
preserve three distinct observations. A complete native committed receipt needs
the authenticated principal, original operation and native revision/parent,
timestamp and digest fields. The client also matches the original target,
expected revision, lifecycle and exact requested/materialized manifest through
the incumbent save state machine. A stored exact `not_applied` receipt is a
read-only no-effect fence, not a receipt miss or the unstored capacity response.
The GET returns its actual authenticated read principal and original lookup key;
neither is accepted from a caller-supplied identity parameter.

The exact incumbent six-field legacy committed shape remains a **legacy recorded
completion** under that authenticated original-key lookup. The response and
client state retain this limited binding explicitly. Shape alone does not prove
a 0028 producer epoch or provide enriched 0030 lineage, durable no-effect or
cutover qualification. Any partial/mixed enrichment refuses; a result marked as
native lineage cannot downgrade to legacy when native fields disappear.

The Saved workspace and standalone scenario capture use the operation-read
settlement path only for their existing GET checks. Neither path calls apply,
reconcile or retry on a read. A bound stored fence disables retry of that original
request and shows useful EN/ZH copy with the draft retained. It is not persisted
as local authority: after reload the existing draft journal is UNKNOWN and must
be read again. Only a deliberate new-draft action may replace that exact retained
command after the current bound fence; an absent/foreign/other-operation result
or local `not_applied` label cannot clear it. Existing direct POST completion
handling and the common CLOSED/OPEN guard remain unchanged.

### Native capture is a separate possible effect

For scenario create/revise, the native source capture can PUT private objects
before the canonical DB operation lock begins. Its current producer has no
durable original-execution completion receipt. A DB `not_applied` fence therefore
means **canonical save not applied, external capture UNKNOWN**, never whole-request
no effect. Handler completion, zero in-flight count, existing retained bytes or
lease expiry cannot settle the original capture.

That outcome keeps the exact command locked, suppresses original mutation retry
and denies new-draft/journal-clear authority. The existing original-key GET remains
available. The journal may retain a conservative `capture_outcome` suppression
marker; it can only keep UNKNOWN/deny a retry, never certify settlement or permit
a new effect. Reload and later inconclusive reads preserve that suppression.
Non-scenario DB fences keep their separately qualified canonical behavior.
