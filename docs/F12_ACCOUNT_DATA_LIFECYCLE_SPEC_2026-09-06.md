### 2.2 Contract
`GET /api/account/export`, `Authorization: Bearer <supabase access token>` → 200 JSON attachment `mastermind-export-<YYYY-MM-DD>.json`; 401 no/invalid token; 429 one export per 15 min per user (in-memory sliding-window throttle, same pattern as the existing brain burst-throttle, `app/main.py:1223-1250` — a fresh per-endpoint dict, not the brain's own, since a rate-limit collision across unrelated endpoints would be its own bug); 503 `{error, partial:false}` **only when zero collections could be read at all** (e.g. a total backend outage) — **round 3 fix for MINOR 2, which found this line contradicting §2.2/§2.3's own `unavailable[]` contract:** a bundle missing one or more collections is never a 503, it is always 200 with those collections listed in `unavailable[]` (§2.5 test 4); `partial:false` on the 503 path describes "no bundle was produced", not "no collection is missing".

The scoping mechanism is the `account_deletions` ledger row stage 7 writes (above): `{user_id, to_email, requested_at, purge_after}`, one row per deletion run, keyed on `(to_email, requested_at)` (round-11 fix for MINOR 3 — see stage 7 above; a re-registration at the same address inside the window inserts its own row rather than colliding with the one being purged). The nightly job is therefore two statements:
`delete from email_log e using account_deletions d where d.purge_after <= now() and e.to_email = d.to_email and e.created_at >= d.requested_at and e.created_at < d.purge_after and (e.user_id = d.user_id or (e.user_id is null and e.created_at < coalesce((select min(u.created_at) from auth.users u where lower(u.email) = lower(d.to_email) and u.created_at > d.requested_at), d.purge_after)));`
`delete from account_deletions where purge_after <= now();`
— the first statement purges every `email_log` row for that `to_email` timestamped at/after the request, once 30 days have passed since the request, **for that account or a bounded signed-out send at that address** (`e.user_id = d.user_id or (e.user_id is null and e.created_at < coalesce(...))` — covering the NULL-`user_id` signed-out-mail case the round-8 predicate missed, round-12 fix, further bounded round-13, both below) and **only** for a `to_email` that has an `account_deletions` row at all — i.e. only for an account that was deleted **through this endpoint**; an account removed from `auth.users` by any other means leaves no ledger row and is never touched by this job. This is the ruling's "for that to_email" scope, applied literally. **The `e.created_at < d.purge_after` upper bound (round-11 fix for MAJOR 3) bounds the window in time; the `e.user_id` clause (round-12 fix for a MAJOR found this same round) bounds it by identity — together they are what makes the scope safe over time:** the time bound alone stops mail sent *after* this ledger row's 30-day window closed (mail timestamped at/after `purge_after`) from ever matching; but round-11's own claim that this made a re-registration's mail safe was **incomplete** — it is only true for a re-registration that happens *after* `purge_after`. A re-registration at the *same address inside* the 30-day window (`t0 < signup < purge_after`, exactly the case §3.2/§3.5 test 13 already contemplates as legitimate) gets its own new `user_id`, but any mail it sends before `purge_after` is still timestamped `>= requested_at` and `< purge_after`, so the time bound alone would still catch it as collateral damage from the *original* account's purge — the false premise this round's review named. The identity clause closes that: an in-window re-registration's own mail carries the NEW account's `user_id`, which matches neither `d.user_id` (the deleted account's id) nor `is null`, so it is excluded regardless of timestamp; mail actually belonging to the deleted account (`e.user_id = d.user_id`) is purged on the identity branch alone, with no further bound needed.

**The `e.user_id is null` branch needed its own bound too (round-13 fix, MAJOR 1 that round):** round-12's null branch purged *any* signed-out row (`e.user_id is null`) inside the `[requested_at, purge_after)` window unconditionally — but a signed-out send is not tied to any account, so it cannot be excluded by comparing `user_id` values the way the round-12 fix excludes an in-window re-registration's own linked mail. A signed-out support message sent to this address *after* someone re-registers at it (but still inside the original 30-day window) would still match this branch and be purged as collateral damage from the original account's deletion, even though it has nothing to do with that account. The predicate now bounds the null branch by a `coalesce` lookup: `e.created_at < coalesce((select min(u.created_at) from auth.users u where lower(u.email) = lower(d.to_email) and u.created_at > d.requested_at), d.purge_after)` — i.e. a NULL-`user_id` row is purged only if it is timestamped strictly before whichever comes first: the earliest re-registration at that address after this request, or (if no such re-registration exists) the ordinary `purge_after` bound. A signed-out row sent before any re-registration is purged on schedule exactly as round-12 already did; one sent after a re-registration is retained. **Stated plainly as a V1 limitation:** signed-out mail sent to a re-registered address after the re-registration is kept until that account itself deletes — there is no signed-out equivalent of the `user_id` identity check, so time-relative-to-re-registration is the only available boundary. **Case-matching asymmetry, named not fixed (round-14 addition, MINOR 2):** the join clause above (`e.to_email = d.to_email`) is case-sensitive, while the coalesce lookup's own `lower(u.email) = lower(d.to_email)` is case-insensitive; a differently-cased `email_log.to_email` row for the same address never satisfies the join at all and is retained indefinitely rather than purged on schedule.
