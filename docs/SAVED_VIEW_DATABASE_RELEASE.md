# Saved-view database release on PR #778

Migration `0035_saved_view_guard.sql` is **source only and unapplied**. It extends the existing `workspace_settings` table with slot metadata, a unique index and an invoker trigger. Existing RLS, table grants, owner IDs, keys and payloads remain the owners of their respective facts. There is no new store or counter service. The migration is one atomic DO statement; the native per-file applier and its catalog readback remain the production route.

The database permits at most 50 active saved views for new writes. An existing population over 50 is preserved, including every payload, and remains readable, renameable and deletable. Further creation refuses until the population falls below 50. Slot uniqueness protects concurrent commits under PostgreSQL isolation; an explicit Repeatable Read or Serializable transaction may instead receive a uniqueness/serialization refusal. The application reads the original UUID after every insertion response and never retries an ambiguous insertion. Only the exact native cap refusal maps to `limit_reached`; message resemblance alone is insufficient.

V2 creation receipts and the saved definition are immutable. A successful rename advances the revision; deletion writes a small tombstone. An older binary's physical DELETE or overwrite of a v2 record refuses. A tombstone cannot be recreated, rewritten or physically deleted by normal authenticated saved-view operations. Legacy records do not acquire invented receipts. The API validates the complete typed definition; the database guard enforces ownership, capacity and receipt transitions, not a second copy of the entire definition/evaluation contract.

Receipts have no automatic expiry. They are retained at least for the account lifetime to preserve request retirement. Tombstones retain UUID, deletion time and the original fingerprint; this is private pseudonymous data, not a claim of anonymization. The inherited `0015` account-delete `SET NULL` behavior still leaves RLS-inaccessible orphan rows. This change preserves that behavior and does not claim account-erasure or orphan-purge acceptance. The current list reader also retains its existing 10,000-setting scan refusal; no unbounded-history claim is made.

Local PostgreSQL uses test auth/team bindings and proves neither hosted Supabase nor authenticated browser behavior. Existing screenshot and browser receipts remain historical evidence for their exact source.

For rollback, keep the v2-compatible reader and database guard. The migration's executable `down` block adds a `NOT VALID` constraint that refuses new saved-row inserts/updates while preserving existing rows, receipt protection and native FK SET NULL. It does not remove the migration. The forward source removes that pause only inside its locked atomic operation. Set `SAVED_VIEW_WRITES_PAUSED=1` in the existing server environment and select it through the normal runtime/deployment path. PUT then refuses every mutation with 503 while authenticated GET and original-ID recovery remain available; unauthenticated calls still return 401. Verify the actual selected behavior. Do not drop receipts, remove the trigger/index, revert to a binary that physically deletes v2 rows, or silently re-enable writes. Restore writes only after the failing release condition is repaired and verified.

The reproducible local database command is `python3 scripts/verify_saved_view_database.py --work-dir <owned-local-evidence-directory> --receipt <receipt.json>`. It starts and stops its own PostgreSQL cluster with a private Unix socket and no TCP listener, uses the repository's actual table/RLS definitions with explicit auth/team test stubs, and never connects to production. Supply `--pg-bin <directory>` if `pg_config` is unavailable. Production application is a separate effect.
